# T018 恢复探测与硬过湿约束开发

## 修正目标

针对T017暴露的恢复死锁，V3增加受限创新恢复通道：当观测有效、变化率风险和执行风险较低、观测与估计差位于接受带内且连续满足确认步数时，允许以低增益逐步校正估计，但不立即把观测标记为完全可信。命令端增加两层硬过滤：可信观测或估计上界达到过湿阈值时禁止灌水；24步滚动灌水量不得超过候选预算。

## 独立开发设计

第三套场景使用新的拉丁超立方、场景和异常分配种子，包含96个开发场景与144个未使用锁定场景，12类异常分别为开发集每类8个、锁定集每类12个。比较基础MPC、V1、V2和8组V3候选，共完成1056次开发运行。锁定场景使用数保持为0。

## 结果与停止决定

8组V3候选在开发集均无安全违反。排序第一的V3C006使用0.01恢复接受带、连续6步确认、0.31过湿阈值和24步16 mm预算；其正常场景非MPC占比中位数为3.42%，相对基础MPC灌水增量中位数为0，相对基础MPC有2类异常中位恶化。

关键晋级条件没有达到：V3C006相对V2改善的异常类型数为0，事件亏缺90分位数为0.441714。传感漂移和阀门卡滞仍出现较大的缺水尾部，说明统一滚动预算虽然限制了过湿，却也限制了执行故障后的补偿灌水。正式开发分类为`NO_V3_CANDIDATE_ADVANCES`，没有生成冻结V3配置，也不运行144个V3锁定场景。

## 方法学含义

继续细调恢复带、确认步数或统一灌水预算，容易变成针对仿真异常的局部调参。下一步应暂停V4式参数搜索，转向毕业设计决策：明确论文主张是基础MPC权衡、异常监督方法学，还是需要最低限度实体数据支持的工程验证；若继续算法路线，应把传感状态估计与执行器可达性分开建模，而不是用同一风险状态和同一预算处理全部故障。

开发轨迹、候选汇总、候选记录和正式JSON连续两次运行SHA-256一致；31项测试通过。
