# T021 平台可靠消息与崩溃恢复软件在环验证

## 目的

在T012任务—命令—反馈审计基础上，验证平台面对重复投递、反馈乱序、命令超时和进程异常退出时，能否保持任务标识、消息顺序、幂等性和版本追溯。该任务只评价本地SQLite消息语义，不评价真实MQTT代理、PLC、网络时延分布或断电耐久性。

## 实现

- 每个任务绑定算法与参数配置SHA-256，注册后不可修改。
- 命令使用`task_id + sequence`作为逻辑主键，`command_id`作为全局幂等键，序号必须连续。
- 反馈同时检查`message_id`和`task_id + sequence`，分别拒绝消息级重复和逻辑重复。
- 先到达的高序号反馈进入持久化缓冲区，只有前序反馈完成或前序命令超时后才按序应用。
- 超时反馈进入审计记录但不应用；超时缺口允许后续已按时到达的反馈继续推进。
- SQLite启用WAL与`FULL`同步。崩溃场景由独立子进程写入已提交状态后调用`os._exit(23)`异常退出，主进程重新打开同一数据库继续处理。

## 场景与结果

共运行4个确定性场景、4个任务、14条命令和16次反馈投递尝试：

1. 重复投递：同一`message_id`和同一逻辑序号的另一消息各拒绝1次；3条反馈只应用3次。
2. 乱序投递：序号2先于1、序号4先于3到达；最终按1、2、3、4应用。
3. 超时与迟到：序号1超时，序号2和3已在截止前到达并缓冲；缺口推进后应用2和3，迟到的序号1被拒绝。
4. 进程崩溃恢复：子进程异常退出前保留3条待完成命令和1条乱序反馈；重新打开数据库后恢复这些状态，并完成序号1至4的单次有序应用。

结果为13条反馈应用、1条命令超时。7项预设约束全部通过：逻辑反馈至多应用一次、反馈按序应用、迟到反馈不应用、超时缺口不阻塞后续反馈、重启保留待处理状态、每个任务绑定版本、无孤立应用反馈。

## 结论边界

结果证明当前Python原型在确定性本地软件在环中具备重复抑制、乱序缓冲、超时推进和已提交状态恢复能力。它不能证明真实MQTT QoS行为、代理重连、跨设备时钟一致性、网络拥塞、数据库文件损坏、操作系统断电或实体泵阀的实时可靠性。后续接入MQTT代理时应复用相同消息键和状态约束，并增加代理断连、重投、时钟偏差和端到端截止时间试验。
