# T022 本地 MQTT 代理与消息链软件在环验证

## 目的

在T021本地SQLite可靠消息语义基础上，引入真实MQTT 3.1.1代理和客户端，验证QoS 1发布订阅、持久会话离线补发、代理异常重启后的自动重连与重新订阅、消息时钟偏差拒绝，以及反馈进入SQLite通道后的幂等和审计一致性。

## 试验实现

- 代理使用aMQTT 0.12.0，独立子进程监听本机回环地址；发布端和订阅端使用Paho MQTT 2.1.0及MQTT 3.1.1协议。
- 所有消息以QoS 1发布，发布端等待PUBACK，订阅端同时核对实际接收QoS。
- 订阅端使用固定客户端标识和`clean_session=False`。代理禁止匿名会话，客户端提供具名身份，使断线期间的QoS 1消息进入持久会话队列。
- MQTT载荷采用固定JSON模式，包含模式版本、消息标识、任务标识、逻辑序号、实际灌水量和源时间戳。进入数据库前先检查模式和源端时钟偏差。
- 有效载荷进入T021的SQLite通道，继续执行消息标识去重、逻辑序号校验、有序应用和任务版本绑定。
- 代理重启通过终止并重新启动独立代理进程实现；客户端网络循环负责检测断开、自动重连和重新订阅。

具名身份只用于形成非匿名持久会话，本任务没有实现密码校验、TLS证书或访问控制，因此不构成通信安全验证。

## 场景与结果

一次完整运行包含26次订阅端接收：20条在线正常反馈、同一应用消息的2次发布、1条断线期间消息、1条代理重启后消息和2条时钟异常消息。最终23条有效反馈被SQLite审计库应用。

8项预设约束全部通过：

1. 20条在线消息全部收到。
2. 订阅端实际接收QoS均为1。
3. 同一`message_id`第二次到达被判定为`duplicate_message`，对应逻辑反馈只应用一次。
4. 订阅端断开后发布的消息在同一持久会话恢复时补发，CONNACK的`session_present`为真。
5. 代理进程异常终止后，发布端和订阅端均检测到断开；新代理启动后两者自动重连，订阅端因原代理内存状态丢失而重新订阅，随后消息成功应用。
6. 源时间戳分别滞后和超前约60秒的消息均在数据库应用前被拒绝。
7. 20条在线消息的本机回环传输时延均低于预设1000 ms检查线，正式结果记录的中位数、95分位数和最大值分别为0.2505、0.3385和0.538 ms。
8. SQLite应用反馈总数与预期23条一致。

完整脚本连续运行3次均通过全部约束，三次在线最大时延为0.435、0.441和0.381 ms。时延是运行时观测，受本机调度影响，不要求跨次哈希一致；结果文件保留最后一次完整运行。

## 结论边界

该结果证明当前Python原型能够在单机真实MQTT代理和客户端链路中完成QoS 1确认、持久会话离线补发、代理重启恢复、应用层幂等、时钟门控和SQLite审计核对。MQTT接收记录中的`DUP`标志均为假，因此本任务没有直接观察到协议层重传；重复抑制证据来自主动重复发布同一应用消息。

本机回环时延不能代表无线网络、跨主机部署或现场控制周期。代理状态仅在内存中，重启后通过客户端重新订阅恢复，没有验证代理持久化存储。当前证据还不覆盖网络丢包与拥塞、TLS和权限控制、设备时钟同步、断电、PLC协议、实体传感器、泵阀响应或红壤控制效果。
